# Student facial references: audit, operation, and validation

## Audit findings

The previous add/update handlers saved a profile photo in `uploads/students`, stored its relative path in `students.IMAGE_PATH`, and copied it to `C:/Biometric_Capstone/known_faces`. A separate bulk uploader wrote up to five additional unlabelled files to that directory without database records. Replacing the primary photo deleted the student's scanner files before replacement succeeded. Changing the LRN could leave filename-derived recognition identities stale.

`recognize_face.py` uses face_recognition/dlib 128-dimensional descriptors, HOG and optional MediaPipe/Haar detection, plus lighting-normalized reference variants. A pickle file and process memory cache avoid repeated enrollment encoding. Previously directory metadata was checked every eight seconds and any change rebuilt all references. A corrupt image could interrupt rebuilding; group enrollment pictures used the first detected face. Scanned frames use EXIF correction, a 480px detection pass, multi-face encoding, lighting/detail fallback passes, and per-student minimum Euclidean distance. Ranking compares students, not individual references, and emits one match per student per frame.

Actual thresholds are **0.60 maximum distance / 0.06 runner-up student margin**, with enhanced passes **0.58 / 0.07**. PHP immediately confirms distances at or below **0.43** and requires two observations within the existing five-second window for other accepted matches. The documented 0.54 ceiling is not the deployed rule. These thresholds remain unchanged; no calibration claim is made. Existing confirmation tracks are session based, rather than a guarantee of uninterrupted consecutive frames; this task preserves their behavior.

The webcam posts to `admin/scan-match.php`. Android `MainActivity.java` posts to `api/mobile-scan.php`, which authenticates the scanner session and includes the same PHP handler. Time In, Lunch Out, Afternoon Time In, Time Out, late calculations, remarks, snapshots, cooldowns, and enrollment checks use that shared attendance code. Those calculations were not changed.

## Database and deployment

Run `C:\xampp\php\php.exe database/migrate_student_face_references.php` before serving scanners after deploying. It is safe to rerun. The helper creates `student_face_references` with `ID`, stable numeric `STUDENT_ID` referencing `students.ID`, an enum and check constraint restricting `POSE` to front/left/right, a unique student/pose key, `IMAGE_PATH`, and creation/update timestamps. The three allowed poses enforce the three-reference maximum. Foreign keys prevent orphan references. No existing student table is recreated.

The migration inserts front metadata pointing to existing `IMAGE_PATH` files; it never copies, deletes, or overwrites photos. New primary photo replacements update both the front record and `students.IMAGE_PATH` inside the student transaction. The numeric relationship survives changes to the editable LRN. Historical unlabelled extra files are retained, but cannot be safely assigned poses automatically; reselect suitable images explicitly in the labeled slots.

Set **BIOMETRIC_PYTHON** in Apache's environment to the full path of the school's working Python executable. The old configured interpreter and `py -3` remain fallbacks. Required packages remain face_recognition/dlib, NumPy, Pillow, and OpenCV; MediaPipe remains optional. This workspace has no usable Python interpreter on PATH or at the old configured location. New photo enrollment fails with an understandable validation-unavailable message until that environment is restored; it does not accept unvalidated photos.

The updated student service binds only to **127.0.0.1:8774**, separating it from stale port-8772 processes. PHP automatically starts it on Windows using the existing startup mechanism. Both service and CLI receive an explicit database-selected list of paths and LRNs. CLI fallback uses a private temporary JSON file, deleted after use. Standalone maintenance invocations without a list retain the historical directory loader. Production scanners always supply a list, including when it is empty.

## Enrollment and validation

Front is required for new enrollments. Existing profiles retain all views unless the administrator uploads replacements or checks an optional-view removal box. The three slots display previews and registration status, use existing theme classes, stack on mobile, and sit side by side on desktop. All three slots offer Use Camera, Choose Photo, and Retake Photo for captures on both Add Student and Edit Student. One shared dialog selects the active pose, displays its instructions, and reuses the chosen device. Captures become JPEG `File` objects assigned with `DataTransfer` to `student_image` (front), `face_left`, or `face_right`; these are ordinary multipart uploads processed by the existing pose-specific validation and storage functions. No base64-only preview state is used by these forms. Camera requests are serialized, tracks stop on cancellation/capture/unload, and canceled permission or canvas results cannot replace another slot. For optional views, capture or upload an unmirrored photo turned toward the student's own left/right. Front cannot be removed; a failed replacement rolls back. Removal is rejected if no readable reference remains.

All uploads, including camera captures, undergo server validation before persistence: JPEG/PNG, maximum 5 MB, at least 480px on each edge, exactly one face, face edge at least 100px, 4% frame margins, Laplacian sharpness at least 35, face grayscale mean 40–220, grayscale standard deviation at least 18, visible eye/nose/mouth landmark geometry, and an upright eye line. Pose is a practical 2D nose/eye-position heuristic: front 0.35–0.65, left 0.58–0.88, right 0.12–0.42. Eye-line slope must be at most 0.30. These are tunable constants in `validate_biometric_image.py`; they are not calibrated yaw-degree measurements. Landmarks are an obstruction proxy, not proof of absence of masks or occlusion, and this is not liveness detection. Confirm these gates with local authorized captures before broad enrollment.

Optional uploads must also match the front descriptor within 0.60; replacing a front verifies retained optional views or asks the administrator to replace/remove inconsistent views. This is a conservative identity-consistency check, not a guarantee that similar-looking people cannot pass. Administrators must verify identity during enrollment. Existing photos are not subjected to stricter enrollment gates merely for continued scanning. Legacy EXIF orientation is corrected in memory without modifying the original file.

## Matching, caching, and rollback

Minimum distance per student remains the aggregation strategy. It preserves the existing behavior and allows the closest pose to contribute without diluting it with unrelated angles. Weighted averaging would require validated pose/quality weights; no held-out dataset was available to establish that it performs better. More references do not relax either distance or ambiguity thresholds. Match deduplication remains per LRN; PHP's existing per-frame deduplication performs one attendance action per identity.

Enrollment/replacement/removal warms the reference cache after commit through the service or CLI. If warm-up fails, the administrator is informed; the next scan refreshes it. Cache fingerprints include the selected student IDs, reference paths, file nanosecond modification times/sizes, cache format version, recognition package versions, and dlib model-file metadata. Unchanged per-file descriptors are reused during partial rebuilds. Unselected references are pruned. Restart loads the disk cache. Bad/missing/group reference files are skipped individually. Writes use a unique temporary file and atomic replacement; disk-cache failure leaves memory matching usable. Matching avoids the previous faces × references × 128 temporary tensor.

For immediate rollback to front-only behavior, set **STUDENT_FACE_REFERENCE_MODE=single** in Apache's environment and restart Apache. Remove the variable to re-enable multiple poses. Both scanners then use the same chosen mode, and the cache fingerprint changes automatically. Keep the new database table and protected file routes during rollback; do not revert photo storage code to a version that expects every path to name a public file. No student or attendance rollback is necessary. Back up the database, protected storage, and historical photos together.

## Privacy and retention

Only administrators can submit photo changes through the existing page guard and CSRF checks. New files have random names in denied `storage/student-faces`, with an Apache deny file installed before photos are written. `IMAGE_PATH` may point to the authenticated `admin/student-face-image.php` route. Historical `uploads/students` URLs are rewritten to that route without changing database values. Administrators can view references; teachers can view only front photos in their current authorized advisory roster; authenticated mobile scanners can view only enrolled students' front photos. Superseded references return 404 from that route. Apache mod_rewrite and authorization modules must remain enabled. Never publish the project through a static server.

Embeddings stay in the local process and the existing denied `.pkl` cache. They are never included in scanner responses or evaluation reports. New uploads do not create redundant scanner-directory copies. Replaced/removed images are deactivated and retained privately; existing images are never deleted automatically. File erasure requires the school's approved retention/deletion process and backup handling. Archived students are excluded from the supplied reference list and remain blocked by the existing PHP enrollment check.

Before collecting student biometrics, the school should approve the notice and consent process, including attendance purpose, who can access images/templates, retention periods, correction/deletion requests, and the available attendance alternative. Maintain an authorized enrollment record, restrict server/backup access, and avoid sending real student photos to external services. This change does not invent a consent record for historical enrollments or set a retention period on the school's behalf.

## Repeatable verification and evaluation

`C:\xampp\php\php.exe tests/student-face-references.test.php` runs database checks using transaction-rolled-back fixtures. It verifies migration reruns, original paths and attendance count, three poses, unique/check/foreign-key constraints, optional removal, continued one-photo eligibility, archived exclusion, final-reference protection, and traversal rejection. The fixture uses a placeholder image solely for path handling, not recognition accuracy.

With the scanner Python environment: `python -m unittest discover -s tests -p test_face_references.py`. These tests use synthetic descriptors and mocked detection for identity aggregation, side-reference participation, ambiguity/unknown rejection, independent group matches, per-frame identity deduplication, cache replace/remove/restart/model invalidation, and enrollment quality failures. Synthetic/mocked tests do not establish biometric accuracy.

Use `python tests/evaluate_face_references.py <private-manifest.json>` for authorized held-out images. The manifest contains `references` entries `{student_id, pose, path}` and `probes` entries `{path, expected_ids, condition}`. Paths are relative to the manifest. Unknown probes use an empty `expected_ids` list; group probes list every expected enrolled identity. Include front, both side angles, different cameras, lighting, blur, unknown people, and similar-looking students. Never reuse enrollment images as probes. Keep both manifest and photos outside public/source directories.

The evaluator runs front-only and multi-reference modes on the same frames, isolates caches from production, and reports unknown-frame FAR, enrolled-face FRR, exact frame identity success, wrong-identity frame count, average/p95 warm recognition latency, cold enrollment latency, and condition breakdowns. FAR here means the fraction of entirely unknown frames with an accepted identity; FRR counts expected enrolled identities missing from the output, including misidentifications. It measures engine recognition, not PHP confirmation or attendance writes. Record dataset sizes, device/server specifications, thresholds, and results before selecting a changed threshold or claiming improvement. Calibration data and final held-out test data must be separate.

`python tests/benchmark_face_matching.py` separately compares the previous distance tensor with the updated matrix calculation for 100, 1,000, and 3,000 synthetic student identities (three views, two lighting variants, eight faces). This measures matching computation only, not live camera or embedding latency.

Local results: migration rerun succeeded with **65 existing front references**, all **14 PHP/database assertions passed**, **10 isolated HTTP authentication/image/traversal/form checks passed**, changed PHP and JavaScript syntax checks passed, and Tailwind CSS built successfully. The HTTP checks render both Add Student and Edit Student and verify their three slots without PHP errors. Anonymous requests to the live Apache historical image route, authenticated image endpoint, and private storage were denied. Android's result-photo requests use the same authenticated OkHttp cookie jar, so protected image delivery preserves its existing request pattern. Python unit tests, camera/mobile end-to-end scans, FAR/FRR, measured recognition latency, scale benchmarks, and visual theme checks could not be completed because the scanner Python environment, camera devices, and authorized held-out dataset were unavailable. No accuracy or latency improvement is claimed.
